# Анализ приложения Investing Demo

## 1. Назначение и технологический стек

Investing Demo — серверное веб-приложение для просмотра каталога акций, актуальных (последних полученных) котировок и графиков дневных цен. Оно также предоставляет формы управления каталогом, регистрацию и вход пользователей, а REST API — операции над теми же записями акций.

Основной стек: Python и Django 5.2; Django REST Framework и django-filter для API; SQLite по умолчанию и PostgreSQL как альтернативная БД; Celery и Redis для фонового обновления цен; Tinkoff Invest API как источник рыночных данных; Plotly для графиков; Bootstrap и django-crispy-forms для веб-интерфейса. Версии основных зависимостей указаны в `requirements.txt`; официальный Tinkoff SDK устанавливается отдельно из `requirements-market.txt`. Описание запуска сервисов PostgreSQL и Redis находится в `docker-compose.yml`, а команды запуска — в `README.md`.

## 3. Архитектура и взаимодействие

Корневые URL в `config/urls.py` направляют `/admin/` в Django Admin, корень сайта — в `dashboard`, а `/user...` — в `user`. В `dashboard/urls.py` определены страницы списка, карточки, создания, редактирования и удаления акции, а также подключён API-маршрут.

HTML-представления в `dashboard/views.py` используют ORM-модель `Share` для чтения и изменения данных в PostgreSQL. Список публичен; создание, редактирование и удаление защищены проверкой аутентификации. Карточка акции получает график через `dashboard/services/graph.py`: сервис при обращении запрашивает у Tinkoff дневные свечи за последние 180 дней и строит HTML-график Plotly. История свечей в локальную базу не записывается.

API в `dashboard/api/v1/` построен на DRF `ModelViewSet` и `ModelSerializer`. Он предоставляет стандартные действия над `Share`; настроены фильтрация по `name` и `ticker`, поиск по `name`, сортировка по `name` и `ticker`, пагинация с размером страницы 100. В представлении API явно не задана авторизация; проект также не задаёт глобальный `DEFAULT_PERMISSION_CLASSES` в показанных настройках.

Цены обновляются отдельной Celery-задачей `dashboard.tasks.update_last_price`. Для каждой акции она вызывает `dashboard/services/market_data.py`, получает последнюю цену из Tinkoff и сохраняет цену, флаг направления и время обновления. Расписание Beat в `config/celery.py` запускает эту задачу с интервалом 5 минут. Брокер Celery настраивается через `CELERY_BROKER_URL` и по умолчанию использует Redis; PostgreSQL и Redis описаны в `docker-compose.yml`. Начальная загрузка инструментов из Tinkoff реализована management-командой `dashboard/management/commands/add_shares.py`.

Регистрация и вход используют встроенную модель пользователя Django. `user/forms.py` проверяет совпадение паролей и наличие пользователя с таким email, а `user/views.py` вызывает Django-аутентификацию и управление сессией. Отдельная модель пользователя в `user/models.py` не объявляется.

## 4. Модель данных

### `dashboard.Share`

Определена в `dashboard/models.py`; первичный ключ создаётся Django автоматически. В модели нет внешних ключей и связей с пользователями.

| Поле | Тип / ограничения | Назначение |
|---|---|---|
| `figi` | `CharField(255)`, уникальное | Идентификатор инструмента для Tinkoff API. |
| `isin` | `CharField(255)` | Международный идентификатор ценной бумаги. |
| `name` | `CharField(255)` | Название компании. |
| `ticker` | `CharField(10)`, уникальное | Биржевой тикер. |
| `currency` | `CharField(20)` | Валюта цены. |
| `uid` | `CharField(255)`, уникальное | Идентификатор инструмента Tinkoff. |
| `last_price` | `FloatField`, nullable/blank | Последняя сохранённая цена. |
| `is_trend_high` | `BooleanField`, nullable/blank | Признак направления цены, используемый в списке. |
| `updated_at` | `DateTimeField(auto_now=True)`, nullable/blank | Время последнего сохранения записи. |

Учётные записи хранятся стандартными моделями Django (`django.contrib.auth`), а не собственной таблицей приложения. В миграциях `dashboard/migrations/` отражена эволюция модели `Share`; миграции Django auth и остальных встроенных приложений поставляются соответствующими зависимостями.

## 5. Пользовательские сценарии и фактические требования

Требования ниже описывают реализованное поведение, а не функции, заявленные только в задании или предполагаемые для инвестиционного приложения.

1. Система отображает публичный постраничный список акций с тикером, названием, ISIN, последней сохранённой ценой и валютой. Если список пуст, показывается сообщение об отсутствии акций. (`dashboard/views.py`, `dashboard/templates/dashboard/list.html`)
2. Пользователь может открыть карточку акции и увидеть её название, текущую сохранённую цену и время обновления. (`dashboard/urls.py`, `dashboard/views.py`, `dashboard/templates/dashboard/detail.html`)
3. При отображении карточки приложение запрашивает дневные свечи акции примерно за последние 180 дней у Tinkoff и выводит график Plotly. Эти исторические данные формируются при запросе и не сохраняются в БД. (`dashboard/services/graph.py`)
4. Неаутентифицированный посетитель может просматривать список и карточку; для HTML-операций добавления, редактирования и удаления требуется аутентификация. При отказе в доступе выполняется перенаправление на главную страницу. (`dashboard/views.py`)
5. Аутентифицированный пользователь может создать запись акции, изменить её или удалить после подтверждения. Форма модели включает все поля `Share`. (`dashboard/forms.py`, `dashboard/views.py`, шаблоны `create.html` и `delete.html`)
6. Посетитель может зарегистрироваться по email и паролю; форма требует совпадения двух введённых паролей и отклоняет email, уже присутствующий в базе. При успешной регистрации пользователь входит в систему. (`user/forms.py`, `user/views.py`)
7. Пользователь может войти по email и паролю и выйти из сессии. При неуспешном входе показывается сообщение об ошибке. (`user/views.py`, `user/urls.py`)
8. REST API `/api/v1/shares/` предоставляет список, получение одной записи, создание, изменение и удаление акций; сериализуются идентификаторы и рыночные поля `Share`. (`dashboard/api/v1/urls.py`, `views.py`, `serializer.py`)
9. API поддерживает фильтрацию по названию и тикеру, поиск по названию и сортировку по названию или тикеру; ответ списка пагинируется по 100 записей. (`dashboard/api/v1/views.py`, `config/settings.py`)
10. Management-команда `add_shares` запрашивает перечень инструментов у Tinkoff и добавляет их в каталог, используя `get_or_create`. (`dashboard/management/commands/add_shares.py`)
11. Фоновая задача периодически получает текущую цену каждого инструмента из Tinkoff, обновляет `last_price` и устанавливает флаг направления относительно предыдущей сохранённой цены. Ошибки отдельного получения цены записываются в лог. (`config/celery.py`, `dashboard/tasks.py`, `dashboard/services/market_data.py`)

## 6. Ограничения, неоднозначности и потенциальные дефекты

- Периодическое обновление цены запускается каждые пять минут. Задача сохраняет время обновления вместе с ценой.
- Цена включает целую и дробную части ответа Tinkoff (`market_data.py`, `graph.py`).
- При первой полученной цене или `last_price=None` система устанавливает `is_trend_high=True`; это значение не обязательно означает реальный рост.
- Исторические цены не сохраняются. Нет интерфейса выбора периода, вычисления доходности или графика на основе накопленной истории.
- API ViewSet не ограничивает CRUD по аутентификации на уровне представления; веб-ограничение в `dashboard/views.py` на API не распространяется.
- Форма `ShareModelForm` редактирует все поля модели, включая `figi`, `uid`, цену и флаг направления; отдельные бизнес-ограничения на ввод этих значений не заданы.
- Настройки Tinkoff, базы данных, секретного ключа, debug-режима, хостов и Celery broker задаются переменными окружения. Без Tinkoff SDK и токена рыночные запросы недоступны; локальные страницы и API могут запускаться на SQLite.
- `user/forms.py` и `user/views.py` проверяют форму входа до аутентификации; регистрация нормализует email и корректно показывает ошибки валидации.
- `dashboard/tests.py` проверяет API, преобразование дробной части цены и обновление цены/времени; `user/tests.py` покрывает базовые сценарии регистрации и входа. Интеграция с внешним Tinkoff API требует отдельного токена и не проверяется этими тестами.
- В проекте не реализованы персональные списки наблюдения, целевые уровни/уведомления, виртуальные портфели и журнал сделок, сохранённая история цен либо симулятор стратегий. Эти возможности перечислены в `HOMEWORK.md` как задания на расширение, а не как существующий функционал.
